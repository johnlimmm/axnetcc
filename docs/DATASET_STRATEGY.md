# RAG 데이터셋 구성 전략

## 결론

하나의 거대한 공용 벡터 DB를 만들지 않는다. `기술 / 보안 / 법무 / 재무`별 코퍼스와 인덱스를 분리하고, 중앙 오케스트레이터는 원문이 아니라 Agent 응답과 근거 식별자만 받는다.

## 데이터의 네 층

1. **공개 원문 코퍼스**
   - 법령, 행정규칙, 공개 가이드, 표준, 공공 조달 문서
   - URL, 제공기관, 시행일, 수집일, 라이선스를 필수 메타데이터로 저장
   - 법령은 법제처 국가법령정보 Open API를 통해 조문 단위로 정기 갱신
2. **실증용 조직 문서**
   - 실제 내부 문서를 바로 넣지 않고 동일 구조의 합성 정책·체크리스트로 먼저 검증
   - 기능 검증 후 비식별·승인된 내부 문서만 별도 폐쇄 인덱스에 추가
3. **질의·정답 평가셋**
   - 예상 Agent, 반드시 포함할 개념, 금지 출력, 기대 근거를 사람이 지정
   - 정상 질문뿐 아니라 개인정보 포함, 권한 부족, 상충 근거 등 공격·경계 사례 포함
4. **운영 로그**
   - 요청 원문 대신 비식별된 요청, 선택 Agent, 근거 ID, 지연, 토큰, 전송량, 정책결정 기록
   - 평가셋과 학습 데이터로 자동 편입하지 않고 검토 큐를 거쳐 승격

## Agent별 최초 권장 범위

| Agent | 최초 코퍼스 | 초기 목표 |
|---|---|---:|
| 기술 | 아키텍처 원칙, RAG 운영기준, SLA, 장애대응 | 20~40문서 |
| 보안 | 데이터 등급, 접근통제, 반출·마스킹, 감사정책 | 20~40문서 |
| 법무 | 개인정보보호법 관련 조문, 위탁계약 체크리스트, 책임규정 | 30~60문서 |
| 재무 | TCO 산정, PoC 예산, 조달 사전검토, 비용상한 | 20~40문서 |

문서 수보다 `한 질문에 필요한 근거가 실제로 검색되는지`가 중요하다. 초기에는 Agent당 20~60개 정도의 검증된 문서로 시작하고 Golden Set의 실패를 기준으로 보강한다.

## 청킹과 메타데이터

- 청크 단위: 제목·조·항·표의 의미 경계를 우선하며 300~700자 권장
- 중복: 동일 문서의 최신 시행본을 기본 인덱스로 두고 구버전은 별도 이력 인덱스에 보존
- 필수 필드: `document_id`, `chunk_id`, `agent`, `title`, `section`, `text`, `source_url`, `effective_date`, `collected_at`, `classification`, `allowed_roles`, `checksum`
- 검색: 키워드(BM25)와 임베딩을 혼합하고 Agent 내에서만 검색
- 근거: 답변 문장마다 최소 한 개의 `chunk_id`를 연결

## 내부 데이터 반입 절차

1. 문서 소유부서와 사용 목적 확인
2. 개인정보·영업비밀·계정정보 탐지
3. 문서등급과 허용 역할 부여
4. 원문 저장소와 벡터 인덱스 암호화
5. 10~20개 검증 질문으로 검색 품질 확인
6. 승인 후 운영 인덱스 승격
7. 만료·개정 문서 자동 비활성화

## 평가 기준

- Agent 선택 Precision / Recall
- Evidence Recall@K, MRR
- 필수 항목 포함률
- 근거 없는 문장 비율
- 민감정보 노출률
- 호출 수, 토큰, 지연, Core-Edge 전송량
- 동일 입력 반복 시 결과 안정성
